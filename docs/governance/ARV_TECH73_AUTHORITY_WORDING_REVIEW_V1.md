# ARV Tech73 Authority Wording Review v1

## 1. Purpose

This document establishes the authority wording review boundary for ARV and ProofOps.

It defines which authority-adjacent words, phrases, labels, headings, UI text, API-facing descriptions, documentation language, repository language, demo language and externally visible statements may be used by public, open-source or externally visible ARV surfaces.

This document does not authorize implementation, publication, release, deployment, packaging, repository exposure, public API exposure, official Evidence Certificate issuance, Evidence Certificate sale, Bundle Evidence Package sale, Dispute Pack sale, public certificate verification service or external distribution.

Its purpose is to prevent accidental legal authority, accidental certification authority, accidental judicial authority, accidental commercial entitlement authority, accidental customer-facing service authority or accidental official ARV issuance authority through wording.

The governing principle remains:

**Proof != Authority**

## 2. Governing Doctrine

Cryptographic evidence may establish integrity, traceability, provenance and internal consistency within the scope of captured evidence.

Authority wording may describe bounded technical verification.

Authority wording must not create legal authority, certification authority, judicial authority, commercial entitlement authority, customer-facing service authority, official ARV issuance authority or official dispute authority.

The canonical local kernel remains governed by the **LOCAL_L0** isolation doctrine.

No public verifier, open-source candidate, local tool, demo, public API, public repository, public document, automated output or deployment surface may represent itself as an official ARV authority.

## 3. Current Controlled-Export Status

Current controlled-export status:

**NO-GO**

The project may continue documentation, private validation, controlled inventory preparation, controlled extraction planning and protection-track execution.

No OSS publication, package release, public artifact, public API release, commercial certificate issuance or external distribution is authorized by this document.

## 4. Allowed Technical Wording

The following wording may be used only within bounded technical verification context:

- cryptographic evidence;
- integrity check;
- file fingerprint;
- SHA-256 fingerprint;
- hash verification;
- bounded artifact;
- technical verification;
- machine-readable verification;
- provenance record;
- traceability record;
- evidence bundle in a non-commercial and non-issuance context;
- validation output;
- local verification result;
- reproducible verification;
- tamper-evident record;
- chain-of-custody data;
- proof of file state;
- proof of execution state;
- proof of timestamped artifact state.

Allowed wording must remain descriptive, technical and bounded.

Allowed wording must not imply legal conclusion, official issuance, court acceptance, customer entitlement, commercial certification or dispute resolution authority.

## 5. Restricted Authority Wording

The following wording is restricted unless separately approved by governance:

- certified by ARV;
- official ARV certificate;
- official evidence certificate;
- ARV-issued proof;
- legally valid proof;
- court-ready proof;
- judicially accepted proof;
- admissible evidence;
- guaranteed authenticity;
- verified truth;
- reality certified;
- official dispute decision;
- dispute resolved by ARV;
- customer-certified evidence;
- commercial certificate issuance;
- authoritative validation;
- authority-grade proof;
- binding proof;
- enforceable proof;
- legal certification;
- official verification authority.

Restricted wording may appear inside governance documents only for exclusion, review, boundary-setting or controlled taxonomy purposes.

Restricted wording must not appear as product promise, public marketing claim, UI label, API claim, README claim, demo claim or customer-facing output.

## 6. Forbidden Authority Claims

No ARV surface may claim or imply that ARV:

- decides legal truth;
- certifies reality;
- replaces a court, judge, notary, regulator or arbitrator;
- guarantees admissibility;
- guarantees legal enforceability;
- issues official customer evidence;
- grants commercial entitlement;
- adjudicates disputes;
- validates a claim beyond the captured evidence boundary;
- confirms the truth of external events not cryptographically captured;
- converts technical proof into legal authority by itself.

Cryptographic verification may support evidence.

It does not create authority.

## 8. Bundle Evidence Package Boundary

Bundle Evidence Package terminology remains protected.

## 10. Public Verifier Wording Boundary

Public verifier wording may describe technical verification only.

Public verifier wording must not describe:

- official ARV certification;
- customer entitlement;
- legal validity;
- judicial acceptance;
- dispute resolution;
- certificate issuance;
- commercial evidence sale;
- protected customer-specific evidence.

A verifier may confirm that a bounded artifact is technically verifiable.

A verifier must not claim that ARV has certified the external truth of the underlying event.

## 11. Machine-Readable Output Boundary

Machine-readable outputs may describe bounded technical fields.

Machine-readable outputs must not include authority-creating fields such as:

- official_certificate_status;
- legal_validity;
- court_admissibility;
- dispute_outcome;
- customer_entitlement;
- certified_truth;
- authority_decision;
- official_arv_issuance.

Machine-readable outputs may use neutral fields such as:

- artifact_hash;
- hash_algorithm;
- verification_status;
- verification_scope;
- generated_at;
- artifact_path;
- evidence_boundary;
- provenance_events;
- validation_warnings;
- local_execution_context.

Any future machine-readable authority-adjacent field requires explicit governance approval.

## 12. UI Copy Boundary

UI copy must remain descriptive and bounded.

Allowed UI copy may include:

- Verify artifact;
- Check hash;
- Generate local proof;
- Export verification record;
- View provenance;
- Validate file integrity;
- Review evidence boundary.

Restricted UI copy includes:

- Certify evidence;
- Issue certificate;
- Confirm legal proof;
- Resolve dispute;
- Guarantee authenticity;
- Create admissible proof;
- Official ARV certificate;
- Court-ready evidence.

UI wording must not create customer-facing reliance beyond the verified technical boundary.

## 13. API Output Boundary

API-facing language must remain machine-bounded and non-authoritative.

API descriptions must not imply:

- certification authority;
- legal authority;
- adjudication;
- customer entitlement;
- commercial issuance;
- official evidence generation.

API outputs may report verification mechanics.

API outputs must not report legal conclusions.

## 14. README and Documentation Boundary

README, docs and repository language may explain technical verification.

README, docs and repository language must not market ARV as an official legal authority, certificate issuer, dispute resolver, notarial substitute, regulator substitute or court substitute.

Documentation may state that cryptographic evidence can support traceability, provenance and integrity.

Documentation must not state that ARV decides truth, legality, admissibility or enforceability.

## 15. Publication Gate

A future public candidate involving authority-adjacent wording remains blocked until the project has completed:

- explicit authority wording boundary approval;
- public verifier wording review;
- certificate terminology review;
- Evidence Certificate terminology review;
- Bundle Evidence Package terminology review;
- Dispute Pack terminology review;
- machine-readable output boundary review;
- API output review;
- UI copy review;
- README and documentation wording review;
- protected commercial terminology exclusion review;
- customer evidence exclusion approval;
- independent governance review;
- signed GO / NO-GO decision.

No technical artifact may bypass the authority wording publication gate.

## 16. Audit Principle

ARV will not create authority by accident.

Any future public authority-adjacent surface must be deliberately allowed, deliberately bounded, minimized, separately reviewed and independently auditable.

The protected certificate, bundle, dispute and commercial issuance system remains isolated behind the governance boundary.
