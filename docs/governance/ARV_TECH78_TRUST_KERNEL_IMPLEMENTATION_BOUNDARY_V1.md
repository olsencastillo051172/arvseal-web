# ARV Tech78 Trust Kernel Implementation Boundary v1

## 1. Purpose

This document establishes the controlled implementation boundary for the ARV Trust Kernel v1 within ARV and ProofOps.

Its purpose is to define what may be implemented as open-source technical infrastructure without creating accidental legal authority, certification authority, adjudicative authority, commercial entitlement authority, official evidence issuance authority or official dispute authority.

The governing principle remains:

**Proof != Authority**

## 2. Controlled Implementation Scope

The ARV Trust Kernel may implement bounded technical proof functions, including:

- canonicalization;
- cryptographic hashing;
- local manifest creation;
- local verification;
- deterministic proof comparison;
- machine-readable proof metadata;
- local/offline proof inspection;
- policy boundary checks;
- repeatable verification routines.

These functions may establish technical integrity, traceability, provenance and internal consistency within the scope of captured evidence.

They do not establish legal truth, official certification, judicial validity, commercial entitlement, dispute resolution authority or official ARV issuance.

## 3. Permitted OSS Kernel Language

The OSS kernel may use technical language such as:

- proof;
- hash;
- digest;
- manifest;
- canonicalization;
- verification;
- local verification;
- cryptographic verification;
- integrity check;
- provenance metadata;
- evidence metadata;
- deterministic output;
- machine-readable proof;
- local proof package;
- verification result;
- validation routine.

Such language must remain bounded to technical verification only.

## 4. Restricted Authority Language

The OSS kernel must not represent itself as:

- a certificate authority;
- an official evidence issuer;
- a dispute authority;
- a judicial authority;
- an adjudicative authority;
- a legal certification authority;
- a commercial entitlement authority;
- an official ARV issuance authority;
- an official dispute resolution service;
- an official public certificate verification service.

The OSS kernel must not imply that a proof output is legally conclusive, commercially enforceable, judicially accepted, independently certified or officially issued by ARV.

## 5. Public Interface Boundary

Any public interface, CLI output, API response, README text, demo text, UI label or generated file must preserve the distinction between:

- technical proof;
- legal authority;
- commercial issuance;
- dispute resolution;
- official certification.

The OSS kernel may say that a file, manifest or proof was technically verified.

It must not say that the evidence was officially certified, legally validated, adjudicated, approved, issued or accepted.

## 6. Output Boundary

The Trust Kernel may generate technical outputs such as:

- proof manifests;
- hash records;
- verification reports;
- JSON proof objects;
- local audit logs;
- deterministic comparison outputs;
- machine-readable verification summaries.

These outputs must not be described as official certificates, official dispute packs, legal findings, judicial determinations, commercial guarantees or ARV-issued evidence certificates unless separately authorized by governance.

## 7. Evidence Certificate Isolation

Evidence Certificate issuance remains outside the OSS Trust Kernel unless explicitly authorized by ARV governance.

The kernel may support future Evidence Certificate infrastructure by producing technical proof inputs.

The kernel itself must not issue, sell, validate, approve or represent an official Evidence Certificate.

## 8. Bundle Evidence Package Isolation

Bundle Evidence Package issuance remains outside the OSS Trust Kernel unless explicitly authorized by ARV governance.

The kernel may support bundling primitives, manifest grouping or proof organization.

The kernel itself must not issue, sell, validate, approve or represent an official Bundle Evidence Package.

## 9. Dispute Pack Isolation

Dispute Pack preparation remains outside the OSS Trust Kernel unless explicitly authorized by ARV governance.

The kernel may support proof organization for future dispute preparation.

The kernel itself must not resolve disputes, adjudicate claims, represent parties, create attorney-client authority, issue legal conclusions or represent an official Dispute Pack.

## 10. Local-First Doctrine

The canonical kernel implementation remains governed by the **LOCAL_L0** isolation doctrine.

The Trust Kernel may run locally and produce local technical verification outputs.

Local execution does not convert ARV into an official authority, public verifier, certificate issuer, dispute authority or legal validation service.

## 11. API Boundary

A future API may expose bounded technical proof functions only after separate governance review.

No API may expose official Evidence Certificate issuance, official Bundle Evidence Package issuance, official Dispute Pack issuance, certificate sale, dispute service, public certificate verification service or official ARV authority without explicit governance authorization.

## 12. Commercial Boundary

The Trust Kernel may be open-source infrastructure.

Commercial products, managed services, certificate issuance systems, bundle sale systems, dispute package systems, paid verification portals and customer-facing official ARV services remain outside this implementation boundary unless separately authorized.

## 13. Audit Principle

ARV will not create authority by implementation accident.

Any technical feature that approaches certificate issuance, evidence packaging, dispute preparation, public verification, public API exposure or commercial entitlement must be deliberately allowed, deliberately bounded, separately reviewed and independently auditable.

## 14. Current Controlled-Export Status

Current controlled-export status:

**NO-GO for public authority or commercial issuance**

The project may continue controlled implementation planning, local kernel preparation, private validation and technical proof infrastructure development.

It does not authorize public release, deployment, packaging, public API exposure, official Evidence Certificate issuance, Evidence Certificate sale, Bundle Evidence Package sale, Dispute Pack sale, public certificate verification service or external distribution.

## 15. Final Rule

ARV may build proof infrastructure.

ARV may implement a Trust Kernel.

But proof is not authority, and the Trust Kernel is not an official ARV authority unless ARV governance explicitly authorizes it.
