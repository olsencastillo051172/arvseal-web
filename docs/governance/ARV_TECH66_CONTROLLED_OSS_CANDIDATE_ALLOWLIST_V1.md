# ARV Tech66 Controlled OSS Candidate Allowlist v1

## 1. Purpose

This document establishes the controlled allowlist doctrine for any future ARV open-source candidate export.

It does not authorize publication, release, packaging, repository exposure, public API release or external distribution.

Its purpose is to define which categories of material may be considered for a deliberately minimized public-candidate surface, and which material must remain excluded behind the governance boundary.

## 2. Governing Doctrine

ARV preserves the foundational distinction:

**Proof != Authority**

Cryptographic evidence may establish integrity, traceability and provenance within the scope of captured evidence. It does not automatically establish absolute material truth, legal validity or judicial authority.

The canonical local kernel remains governed by the **LOCAL_L0** isolation doctrine.

No allowlist entry may transform protected commercial implementation into public material by inertia, convenience, tooling default, repository structure or packaging pressure.

## 3. Current Controlled-Export Status

Current controlled-export status:

**NO-GO**

The project may continue documentation, private validation, controlled inventory preparation, controlled extraction planning and protection-track execution.

No OSS repository, public package, public artifact, public API release or external distribution is authorized by this document.

## 4. Allowlist Principle

A future OSS candidate may include only material that is:

- intentionally selected;
- minimized;
- technically separable;
- independently reviewed;
- cryptographically fingerprinted;
- compatible with the controlled candidate inventory;
- extracted through the controlled extraction procedure;
- free from protected commercial implementation details;
- free from production credentials, secrets and signing material;
- free from protected trademarks, emblems and certification seals.

The allowlist is a positive inclusion boundary.

Anything not expressly allowed remains excluded.

## 5. Candidate Allowlist Classes

### 5.1 Class A - Presumptively Reviewable Public Candidate

Class A material may be considered for a future minimized OSS candidate after technical, legal and governance review.

Potentially reviewable Class A material includes:

- neutral technical specifications;
- public data schemas;
- deterministic verification examples;
- reproducible test vectors;
- portable local verification interfaces;
- narrowly scoped LOCAL_L0 verification logic;
- public-facing documentation expressly approved for release;
- license notices;
- attribution notices;
- reproducible local smoke tests;
- neutral sample artifacts that do not expose protected implementation details.

Class A status does not authorize publication by itself.

### 5.2 Class B - Conditional Review Candidate

Class B material requires explicit written review before it may be promoted into any public candidate.

Conditional Class B material includes:

- SDK wrappers;
- interoperability adapters;
- packaging metadata;
- CLI presentation layers;
- public API documentation;
- reference implementation fragments;
- sample integrations;
- developer tooling;
- reusable validation helpers;
- generated examples.

Class B material may not be published until it is separately reviewed for boundary leakage, dependency exposure, licensing, trademarks, credentials, telemetry and commercial coupling.

### 5.3 Class P - Protected Material

Class P material must remain private, managed or separately governed.

Protected material includes, at minimum:

- official ARV Snap issuance;
- ProofOps commercial orchestration;
- Baul de pruebas;
- Evidence Certificate;
- Bundle Evidence Package;
- Dispute Pack;
- Policy Engine;
- Dispute Logic;
- enterprise API;
- managed Gateway;
- productive adapters;
- privileged connectors;
- telemetry;
- internal measurement mechanisms;
- signing keys;
- secrets;
- production credentials;
- private configuration;
- production tokens;
- private implementation logic;
- protected trademarks;
- emblems;
- certification seals;
- commercial workflow templates;
- non-public roadmap logic;
- customer-specific operational evidence;
- non-public dispute automation logic.

Protected classification overrides allowlist ambiguity.

Current approved public-candidate allowlist:

**EMPTY**

## 7. Allowlist Entry Requirements

Before any item may enter a future approved allowlist, the entry must identify:

- repository-relative path;
- candidate class;
- extraction rationale;
- review owner;
- technical review status;
- legal review status;
- governance review status;
- licensing status;
- dependency status;
- secret-scan status;
- credential-scan status;
- trademark status;
- test status;
- source commit;
- extracted artifact hash;
- per-file SHA-256 fingerprint;
- aggregate manifest SHA-256;
- signed GO / NO-GO decision reference.

No wildcard inclusion is permitted unless separately justified, reviewed and approved.

## 9. Public Candidate Surface Rule

A future public candidate must be deliberately minimized.

The public surface may be prepared only around:

- specification;
- reproducibility;
- verification;
- interoperability;
- local testing;
- auditability;
- educational clarity.

The public surface must not expose:

- production orchestration;
- commercial decision logic;
- privileged execution paths;
- customer-specific operational systems;
- private dispute strategy;
- private managed-service logic;
- certification authority mechanisms;
- signing infrastructure;
- credentialed connectors.

## 10. Required Reviews Before Allowlist Approval

Before any future allowlist is approved, the project must complete:

- controlled candidate inventory review;
- controlled extraction procedure review;
- explicit file-level allowlist review;
- protected-surface exclusion review;
- dependency review;
- license review;
- contributor-governance review;
- trademark and seal review;
- secret and credential scanning;
- telemetry review;
- reproducible local smoke-test review;
- independent governance review;
- signed GO / NO-GO decision.

Every future approved allowlist must generate an allowlist manifest containing:

- source repository identifier;
- source branch;
- source commit;
- allowlist version;
- extraction procedure version;
- approved candidate file list;
- excluded protected categories;
- per-file SHA-256 fingerprints;
- aggregate manifest SHA-256;
- build and smoke-test result references;
- dependency review reference;
- license review reference;
- secret-scan reference;
- credential-scan reference;
- signed GO / NO-GO decision reference.

The allowlist manifest must be preserved as an auditable governance artifact.

## 12. Publication Gate

A future public candidate remains blocked until the project has completed:

- candidate inventory approval;
- extraction procedure approval;
- explicit allowlist approval;
- protected-surface exclusion approval;
- dependency and license review;
- secret and credential scanning;
- reproducible local smoke tests;
- independent governance review;
- signed GO / NO-GO decision.

No technical artifact may bypass the publication gate.

## 13. Audit Principle

ARV will not publish its private repository by inertia.

Any future public export must be deliberately allowed, deliberately extracted, minimized, separately reviewed and independently auditable.

The protected commercial system remains isolated behind the governance boundary.
