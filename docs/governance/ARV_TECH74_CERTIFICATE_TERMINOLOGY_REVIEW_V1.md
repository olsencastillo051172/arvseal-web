# ARV Tech74 Certificate Terminology Review v1

## 1. Purpose

This document establishes the certificate terminology review boundary for ARV and ProofOps.

It defines which certificate-adjacent words, phrases, labels, headings, UI text, API-facing descriptions, documentation language, repository language, demo language and externally visible statements may be used by public, open-source or externally visible ARV surfaces.

This document does not authorize implementation, publication, release, deployment, packaging, repository exposure, public API exposure, official Evidence Certificate issuance, Evidence Certificate sale, Bundle Evidence Package sale, Dispute Pack sale, public certificate verification service or external distribution.

Its purpose is to prevent accidental certification authority, accidental official certificate issuance, accidental legal certificate status, accidental customer-specific evidence exposure, accidental commercial entitlement or accidental public proof authority through certificate terminology.

The governing principle remains:

**Proof != Certificate Authority**

## 2. Governing Doctrine

Cryptographic evidence may establish integrity, traceability, provenance and internal consistency within the scope of captured evidence.

Certificate terminology may describe bounded technical verification only.

Certificate terminology must not create legal certification authority, accreditation authority, judicial authority, commercial entitlement authority, customer-facing service authority, official ARV issuance authority or official dispute authority.

The canonical local kernel remains governed by the **LOCAL_L0** isolation doctrine.

No public verifier, open-source candidate, local tool, demo, public API, public repository, public document, automated output or deployment surface may represent itself as an official certificate issuer.

## 4. Allowed Certificate-Neutral Uses

The following uses may be allowed only when they remain descriptive, bounded and non-authoritative:

- file integrity proof;
- cryptographic verification record;
- verification artifact;
- proof bundle;
- evidence record;
- validation output;
- audit artifact;
- local proof record;
- timestamped verification output;
- hash-based verification record;
- provenance record;
- chain-of-custody record.

These terms must not imply official certificate issuance unless later approved by governance.

## 5. Restricted Certificate Terms

The following terms are restricted in public, open-source or externally visible surfaces:

- certificate;
- certified;
- certification;
- certifier;
- certificate authority;
- official certificate;
- legal certificate;
- judicial certificate;
- admissibility certificate;
- ARV certificate;
- ProofOps certificate;
- Evidence Certificate;
- Bundle Evidence Certificate;
- dispute certificate;
- customer certificate;
- verified certificate.

Restricted terms may be referenced only in governance documents, internal planning, protected commercial planning or terminology review contexts.

## 6. Evidence Certificate Isolation

Evidence Certificate remains a protected commercial and governance-controlled concept.

No public repository, demo, verifier, local tool, automated output, README, API response, UI copy or open-source candidate may issue, simulate, preview, price, sell or imply availability of an Evidence Certificate.

Evidence Certificate terminology remains isolated until explicitly approved by later governance.

## 7. Public Verifier Constraint

A public verifier may verify technical facts.

A public verifier must not issue certificates.

A public verifier may state that a hash matches, a timestamp exists, a file was checked or a verification record is internally consistent.

A public verifier must not state that a document is officially certified, legally certified, judicially certified, commercially certified or ARV-certified.

## 8. API Constraint

API-facing descriptions may expose bounded verification facts only.

API-facing descriptions must not expose certificate status, certificate issuance, certificate ownership, certificate sale, Evidence Certificate status, customer entitlement, dispute-pack entitlement or official ARV authority.

Any API field resembling `certificate`, `certified`, `certification`, `issuer`, `authority`, `official`, `evidenceCertificate`, `certificateId` or `certificateStatus` remains blocked unless later approved.

## 9. UI Copy Constraint

UI copy may use neutral technical language.

Preferred UI language includes:

- Verify file;
- Check proof;
- View verification record;
- Validate hash;
- Confirm timestamp;
- Inspect evidence record;
- Review proof bundle.

UI copy must not use:

- Get certified;
- Issue certificate;
- Official certificate;
- Certified by ARV;
- Court-certified;
- Legally certified;
- Buy certificate;
- Claim certificate;
- Evidence Certificate available.

## 10. README and Documentation Constraint

README and public documentation may describe ARV as a cryptographic evidence, proof, verification and provenance system.

README and public documentation must not describe ARV as a certification authority, legal certifier, official evidence certifier, adjudicator, court-admissibility guarantor or dispute authority.

Any certificate-adjacent wording must remain framed as governance-controlled and not yet authorized.

## 11. Repository Constraint

Repository names, branch names, issue titles, pull request titles, file names and public labels must avoid implying certificate issuance.

Governance documents may contain certificate terminology when the purpose is explicitly to restrict, review or govern that terminology.

No repository artifact may imply that an open-source candidate is already an official certificate product.

## 12. Demo Constraint

A demo may show technical verification.

A demo must not issue certificates.

A demo must not display certificate IDs, certificate claims, customer certificates, legal certificate language, judicial certification language, Evidence Certificate purchase flows or commercial certificate entitlement.

A demo may show sample verification records only when clearly bounded and non-authoritative.

## 13. Customer Evidence Constraint

Customer-specific evidence remains protected.

Certificate terminology must not be used to expose, summarize, certify, package, sell or externally distribute customer-specific evidence.

Any customer-facing certificate surface remains blocked until separately approved by governance.

## 14. Commercial Boundary

Certificate terminology may create accidental commercial expectations.

The following remain blocked:

- paid certificate issuance;
- Evidence Certificate sale;
- certificate verification subscription;
- certificate entitlement;
- customer certificate dashboard;
- certificate package;
- certified dispute pack;
- certificate download;
- certificate registry;
- certificate verification service.

Commercial certificate terminology requires separate governance authorization.

Any future certificate-adjacent surface must be deliberately allowed, deliberately bounded, minimized, separately reviewed and independently auditable.

The protected certificate, bundle, dispute and commercial issuance system remains isolated behind the governance boundary.
