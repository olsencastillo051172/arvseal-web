# ARV Tech79 OSS License Trademark Governance Boundary v1

## 1. Purpose

This document establishes the controlled governance boundary for ARV open-source licensing, trademark use, fork policy, commercial use, contribution provenance and official authority separation.

It exists to prevent accidental surrender of ARV business authority, brand authority, evidence issuance authority, certificate authority, dispute authority, commercial entitlement, closed vertical control, custody authority or official verification authority through public repository exposure.

This document is a governance and technical boundary document only.

It does not itself grant a license, publish a license, authorize release, authorize public deployment, authorize commercial use, authorize official Evidence Certificate issuance, authorize Bundle Evidence Package sale, authorize Dispute Pack sale, authorize trademark use, authorize logo use, authorize fork endorsement, authorize public verifier operation, authorize CRL operation or authorize external distribution.

The governing principle remains:

**OSS Core != Official ARV Authority**

## 2. Governing Doctrine

ARV may publish a minimal open-source technical core.

ARV may allow public inspection, controlled contribution and technical reuse of bounded proof infrastructure.

But public code does not equal public brand license.

Public code does not equal official issuer authority.

Public code does not equal Evidence Certificate authority.

Public code does not equal Bundle Evidence Package authority.

Public code does not equal Dispute Pack authority.

Public code does not equal commercial service authority.

Public code does not equal customer-facing ARV authority.

Public code does not equal right to use ARV name, ARV marks, ARV logos, ARV certificate identifiers, ARV seal language, ARV issuer language, ARV numbering, ARV registry references, ARV CRL references or ARV official verification claims.

The canonical local kernel remains governed by the **LOCAL_L0** isolation doctrine.

The canonical authority boundary remains:

**Proof != Authority**

## 4. OSS Technical Core Boundary

The OSS technical core may include only bounded proof infrastructure.

Permitted OSS-adjacent technical areas may include, if separately approved:

- canonicalization primitives;
- cryptographic hashing;
- local manifest generation;
- deterministic local proof packaging;
- local verification routines;
- CLI-only developer tooling;
- test fixtures;
- documentation for non-official proof generation;
- machine-readable technical outputs clearly marked as non-official;
- examples that do not imply ARV authority.

The OSS technical core must not include protected commercial issuance infrastructure unless separately authorized by ARV governance.

The OSS technical core must not include private keys, signing authority, commercial issuer logic, official certificate numbering, official registry credentials, official verification backend, private customer workflows, protected vertical playbooks, paid dispute templates, paid Evidence Certificate templates, paid Bundle Evidence Package templates or protected custody infrastructure.

## 5. Closed Commercial Boundary

The following surfaces remain closed, restricted, separately licensed or contract-controlled unless ARV governance explicitly authorizes otherwise:

- official Evidence Certificate issuance;
- official Evidence Certificate sale;
- official Bundle Evidence Package sale;
- official Dispute Pack sale;
- official public verifier;
- official issuer registry;
- official CRL / revocation registry;
- protected commercial API;
- hosted backend;
- enterprise dashboard;
- private evidence vault;
- custody ledger;
- branded verification seal;
- official certificate numbering;
- official certificate rendering;
- official legal/dispute packaging templates;
- vertical-specific commercial workflows;
- customer-specific evidence workflows;
- protected automation agents;
- production signing keys;
- production release keys;
- commercial trust kernel extensions.

No public repository artifact may imply that these surfaces are included in the OSS core.

## 6. Trademark and Logo Boundary

The ARV name, ARV mark, ARV seal, ARV logo, product names, official certificate names, issuer names, project branding, authority language and commercial identifiers are not granted merely because source code is visible or licensed.

Forks, mirrors, derivatives, packages, deployments or integrations must not represent themselves as official ARV unless explicitly authorized by ARV governance.

Third parties must not use ARV marks in a way that suggests sponsorship, certification, issuance, partnership, endorsement, official verification, official certificate authority, official dispute authority, official registry authority or customer-facing ARV service authority.

Permitted nominative references, if any, must remain bounded, factual and non-confusing.

The governing principle remains:

**Fork != Official ARV**

## 7. Fork Policy Boundary

A fork may exist as an independent technical derivative only if allowed by the applicable code license.

But a fork is not official ARV.

A fork must not:

- claim ARV official status;
- use ARV logos as its own branding;
- issue official ARV certificates;
- issue official ARV Evidence Certificates;
- issue official ARV Bundle Evidence Packages;
- issue official ARV Dispute Packs;
- operate an official ARV verifier;
- operate an official ARV CRL;
- use ARV certificate numbering;
- imply official ARV custody;
- imply ARV endorsement;
- imply ARV legal authority;
- imply ARV adjudicative authority;
- imply ARV customer service authority;
- imply ARV commercial authorization.

A fork may be technically compatible without being officially authorized.

Compatibility is not endorsement.

Interoperability is not authority.

Public derivation is not official issuance.

## 8. Commercial Use Boundary

Any commercial use of the OSS technical core must be evaluated separately from use of ARV trademarks, official issuance, hosted services, protected verticals, commercial templates and official verification authority.

A code license may allow technical reuse.

That does not automatically grant:

- ARV brand rights;
- ARV logo rights;
- ARV certificate issuance rights;
- ARV hosted service rights;
- ARV commercial product rights;
- ARV official verifier rights;
- ARV registry rights;
- ARV CRL rights;
- ARV dispute packaging rights;
- ARV customer-facing authority.

The project must not accidentally convert public technical code into public commercial entitlement.

The governing principle remains:

**Code License != Brand License**

## 9. License Selection Boundary

Final license selection remains a controlled governance decision.

Potential licensing lanes may include:

- permissive OSS license for narrow technical proof primitives;
- file-level reciprocal OSS license for selected proof core files;
- source-available license for protected commercial surfaces;
- proprietary license for issuer, registry, certificate, bundle, dispute, vertical and hosted systems;
- separate trademark policy;
- separate contributor policy;
- separate commercial terms;
- separate enterprise terms;
- separate API terms.

No repository text, README, package metadata, UI copy or API description may imply that final licensing has been approved until an explicit signed GO decision exists.

## 10. Contribution Provenance Boundary

ARV must preserve contribution provenance.

Before accepting public contributions, ARV governance should define and implement a contribution path covering:

- contributor identity expectations;
- DCO or CLA decision;
- sign-off requirements;
- contributor license grant;
- IP provenance statement;
- third-party dependency disclosure;
- generated-code disclosure;
- AI-assisted contribution disclosure, if required by policy;
- review authority;
- CODEOWNERS approval;
- record retention;
- contribution audit trail.

No public contributor may acquire ARV authority merely by contributing code.

Contribution does not grant brand rights.

Contribution does not grant issuer rights.

Contribution does not grant commercial rights.

Contribution does not grant official governance authority.

## 11. Technical Governance Boundary

Before public release, ARV governance should define and implement repository controls covering:

- branch protection;
- required pull request review;
- CODEOWNERS;
- required status checks;
- signed commits or signed tags where appropriate;
- release signing;
- protected release branches;
- secret scanning;
- dependency review;
- SBOM generation;
- provenance records;
- build reproducibility policy;
- vulnerability disclosure policy;
- security contact policy;
- release approval gates;
- revocation and incident response procedure.

No technical control should rely only on informal trust.

The repository itself must enforce the governance boundary wherever possible.

## 12. Release Signing and Supply-Chain Boundary

No public artifact may be treated as an official ARV release unless the release process has been separately approved.

Official release governance should cover:

- release owner;
- release checklist;
- signed tag;
- signed artifact;
- artifact hash;
- SBOM;
- dependency inventory;
- changelog;
- provenance statement;
- release notes;
- security review;
- rollback procedure;
- revocation procedure;
- public verification instructions.

A build artifact is not an official ARV release merely because it exists.

A deployment preview is not an official ARV release.

A package is not an official ARV release unless ARV governance explicitly authorizes it.

## 13. CRL and Revocation Boundary

Any ARV CRL, certificate revocation list, issuer revocation list, key revocation list, registry invalidation list or public status registry remains protected infrastructure.

No OSS component may create, simulate or imply official CRL authority unless separately authorized.

Test fixtures may use mock revocation data only if clearly marked as non-official.

The official revocation surface remains isolated behind governance approval.

The governing principle remains:

**Revocation Authority != Demo Data**

- ownership of ARV marks;
- ownership of ARV logos;
- ownership of commercial engine IP;
- ownership of protected vertical workflows;
- ownership of certificate issuance logic;

- assignment of employee/contractor work product;

## 16. Third-Party Claims Boundary

Third parties may not use ARV technical outputs to create false or confusing claims.

ARV proof outputs may establish bounded technical facts such as hash, timestamp, manifest structure, local consistency, provenance metadata or verification result.

ARV proof outputs do not by themselves establish legal authority, official dispute resolution, official certification, official adjudication, official custody, official registry membership or official commercial entitlement.

Any third-party claim beyond bounded technical verification is outside ARV official authority unless separately authorized.
