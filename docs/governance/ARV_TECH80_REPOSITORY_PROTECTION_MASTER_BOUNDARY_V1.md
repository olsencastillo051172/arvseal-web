# ARV TECH80 Repository Protection Master Boundary v1

## 1. Purpose

This document establishes the master repository protection, licensing, trademark, fork, contribution, custody and commercial-governance boundary for ARV and ProofOps.

It exists to prevent accidental surrender of ARV business authority, brand authority, certification authority, Evidence Certificate authority, Bundle Evidence Package authority, Dispute Pack authority, CRL authority, official verifier authority, closed vertical authority, commercial entitlement authority or customer-facing ARV authority through public repository exposure.

This document is a governance boundary document only.

It does not publish a license, grant a code license, grant trademark rights, authorize public release, authorize deployment, authorize commercial use, authorize fork endorsement, authorize official Evidence Certificate issuance, authorize Bundle Evidence Package sale, authorize Dispute Pack sale, authorize public certificate verification, authorize CRL operation, authorize external distribution or authorize any official ARV service.

The governing principle is:

**Open Source Core != Official ARV Authority**

## 2. Governing Doctrine

ARV may publish a narrow, auditable, minimal open-source technical core.

ARV may allow public inspection, controlled contribution and technical reuse of bounded proof infrastructure.

But public code does not equal public brand license.

Public code does not equal official issuer authority.

Public code does not equal Evidence Certificate authority.

Public code does not equal Bundle Evidence Package authority.

Public code does not equal Dispute Pack authority.

Public code does not equal CRL authority.

Public code does not equal official verifier authority.

Public code does not equal commercial service authority.

Public code does not equal customer-facing ARV authority.

Public code does not equal closed vertical authority.

Public code does not equal right to represent, certify, adjudicate, resolve, issue, revoke, verify, validate, sell or operate as ARV.

## 5. OSS Core Boundary

The OSS Core may contain narrow technical proof infrastructure, including canonicalization utilities, cryptographic hashing, local manifest generation, local proof validation, deterministic evidence formatting, local verification helpers, non-authoritative proof examples, non-commercial demo scaffolding and repository-facing documentation.

The OSS Core must not contain official Evidence Certificate issuance logic, certificate authority logic, commercial entitlement logic, paid certificate workflow logic, official verifier service logic, CRL operation logic, revocation authority secrets, private signing keys, customer custody workflows, dispute-resolution authority logic, closed vertical business logic, billing logic, proprietary trust engines, production credentials or production infrastructure secrets.

## 6. License Architecture Boundary

TECH80 does not select the final code license.

The license architecture must be decided in TECH81.

TECH81 must map each component to one of the following categories:

- open-source permissible core;
- open-source restricted-risk component;
- source-available component;
- commercial-license-only component;
- private internal component;
- non-distributable authority component.

No LICENSE file may be published as final until TECH81 is approved.

No repository may imply that ARV brand rights, certification rights, verifier rights, CRL rights, customer-facing rights or commercial service rights are granted by the code license.

## 7. Trademark and Brand Boundary

The ARV name, ARV logos, ProofOps brand, Evidence Certificate terminology, Bundle Evidence Package terminology, Dispute Pack terminology, certificate templates, official verifier language and public authority language remain protected brand and authority assets.

A fork may use the code only within the limits of the applicable code license.

A fork may not present itself as ARV, official ARV, ARV-certified, ARV-compatible unless expressly allowed by policy, ARV Evidence Certificate issuer, ARV Bundle Evidence Package issuer, ARV Dispute Pack provider, ARV verifier, ARV CRL operator, ARV authorized service, ARV partner or ARV commercial implementation.

Trademark, logo and official-authority use require explicit written authorization.

## 8. Fork Policy Boundary

Forks are technically permitted only to the extent permitted by the applicable code license.

Forks are not official ARV.

Forks are not endorsed by ARV.

Forks may not use ARV names, marks, logos, certificate templates, official verifier statements or authority language unless separately authorized.

Forks must not imply custody, certification, verification, adjudication, dispute resolution, issuance, revocation or commercial authority.

Forks that modify proof behavior must identify themselves as modified and non-official.

Forks that remove attribution, alter provenance, simulate official issuance, spoof official verification, copy brand surfaces or confuse users may be subject to enforcement.

## 9. Contributor Governance Boundary

External contributions require provenance controls.

TECH83 must define and implement the contribution model.

The default governance direction is DCO for ordinary low-risk contributions and CLA or equivalent written IP control for critical files, authority-adjacent files, licensing files, certificate-adjacent files, verifier-adjacent files, CRL-adjacent files, commercial-engine-adjacent files and governance documents.

CODEOWNERS must protect critical paths.

No external contribution may be accepted into critical paths without explicit governance approval.

## 10. Supply Chain and Release Integrity Boundary

TECH85 must define release integrity controls.

Before public release, ARV must establish SBOM generation, provenance records, signed release artifacts, published checksums, controlled build procedures, dependency review, vulnerability scanning, release approval gates, rollback procedures and revocation procedures.

No public release may occur without release integrity approval.

## 11. GitHub Security and Repository Controls

TECH84 must define repository security controls.

Required controls include branch protection, rulesets, required status checks, secret scanning, dependency scanning, static analysis, dependency update automation, protected environment rules, least-privilege repository access, audit log review, blocked force-push on protected branches and protected tag strategy for releases.

No production-facing repository may be public without TECH84 approval.

## 12. Commercial Engine Isolation

The commercial engine must remain isolated from the OSS Core.

The commercial engine includes Evidence Certificate issuance, Bundle Evidence Package issuance, Dispute Pack issuance, customer-specific workflows, paid service logic, billing and entitlement systems, official verifier service, CRL service, revocation logic, certificate signing logic, production custody ledger, official authority registry and closed vertical workflows.

TECH86 must define technical fences and CI gates that prevent accidental publication of private or commercial modules.

## 13. CRL and Official Verifier Boundary

The CRL and official verifier are authority-bearing systems.

They must remain outside the public OSS repository unless explicitly authorized by governance.

TECH87 must define CRL architecture, signing authority, revocation workflow, key custody, access control, audit logs, backup and disaster recovery, verifier trust model, public/private boundary and anti-spoofing controls.

No CRL, revocation or official verifier service may be publicly operated without TECH87 approval.

## 14. SRL and IP Governance Boundary

Corporate ownership, assignment and IP protection must be handled outside the repository.

TECH88 must define SRL IP ownership clauses, founder assignment, employee assignment, contractor assignment, contributor assignment, trademark ownership, logo ownership, repository ownership, domain and infrastructure ownership, custody of private signing keys, authority to approve commercial licenses and authority to enforce brand misuse.

No public launch may occur without IP ownership review.

## 15. Enforcement Boundary

TECH89 must define the enforcement playbook.

The playbook must include trademark misuse response, fork confusion response, false certificate response, false verifier response, unauthorized commercial use response, takedown templates, legal escalation matrix, evidence preservation protocol, public communication protocol and abuse monitoring procedure.

Enforcement must protect ARV without confusing open technical proof with official ARV authority.

## 16. Public Launch Gate

TECH90 is the public launch readiness gate.

No public launch may occur unless TECH80 through TECH89 are approved.

TECH90 requires explicit GO / NO-GO decision.

Default status remains:

**NO-GO**
