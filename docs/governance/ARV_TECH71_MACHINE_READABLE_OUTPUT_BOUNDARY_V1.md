# ARV Tech71 Machine-Readable Output Boundary v1

## 1. Purpose

This document establishes the machine-readable output boundary for ARV and ProofOps.

It defines which structured fields, machine-readable claims, verification outputs, JSON records, API-facing summaries, receipts, manifests, validation reports or automation-readable artifacts may be exposed by public, open-source or externally visible ARV surfaces.

This document does not authorize implementation, publication, release, deployment, packaging, repository exposure, public API exposure, official Evidence Certificate issuance, Evidence Certificate sale, Bundle Evidence Package sale, Dispute Pack sale, public certificate verification service or external distribution.

Its purpose is to prevent accidental authority, accidental certification, accidental entitlement, accidental commercial issuance or accidental customer-specific evidence exposure through machine-readable outputs.

The governing principle remains:

**Proof != Authority**

## 2. Governing Doctrine

Cryptographic evidence may establish integrity, traceability, provenance and internal consistency within the scope of captured evidence.

Machine-readable output may describe bounded technical verification.

Machine-readable output must not create legal authority, certification authority, judicial authority, commercial entitlement authority, customer-facing service authority or official ARV issuance authority.

The canonical local kernel remains governed by the **LOCAL_L0** isolation doctrine.

No public verifier, open-source candidate, local tool, demo, public API, public repository, public document, automated output or deployment surface may represent itself as an official ARV certificate authority.

## 4. Machine-Readable Output Boundary

Machine-readable outputs include, without limitation:

- JSON outputs;
- receipt payloads;
- verification manifests;
- hash reports;
- provenance records;
- validation summaries;
- structured audit records;
- downloadable metadata files;
- API responses;
- command-line machine-readable output;
- CI artifacts;
- public verifier output;
- future controlled export output.

A machine-readable output is not merely technical formatting.

A machine-readable output can become a product claim, commercial claim, certification claim, legal claim or authority claim if it is not bounded.

## 5. Allowed Public Output Claims

A public, open-source or externally visible output may state only bounded technical facts, such as:

- artifact hash;
- file size;
- digest algorithm;
- local timestamp if available;
- verification timestamp if available;
- verification status of a bounded artifact;
- internal consistency result;
- chain linkage result;
- manifest consistency result;
- detached signature presence if applicable;
- non-authoritative validation result;
- non-certificate technical verification result.

Allowed wording must remain technical, bounded and non-institutional.

## 6. Forbidden Output Claims

A public, open-source or externally visible output must not state or imply:

- legal validity;
- judicial validity;
- official certification;
- ARV certificate issuance;
- Evidence Certificate issuance;
- Evidence Certificate sale;
- Bundle Evidence Package sale;
- Dispute Pack sale;
- customer entitlement;
- commercial entitlement;
- dispute outcome;
- court acceptance;
- regulatory acceptance;
- identity authority;
- ownership authority;
- authorship authority;
- institutional endorsement;
- official ARV assurance;
- customer-specific service completion.

## 7. Evidence Certificate Boundary

Machine-readable output may not use Evidence Certificate language unless explicitly approved through a future certificate issuance boundary.

A technical verification receipt is not an Evidence Certificate.

A public validation output is not an Evidence Certificate.

A hash manifest is not an Evidence Certificate.

A public verifier response is not an Evidence Certificate.

## 8. Bundle Evidence Package Boundary

Machine-readable output may not represent itself as a Bundle Evidence Package.

A collection of files, hashes, manifests, logs or validation outputs is not a Bundle Evidence Package unless issued through an authorized commercial issuance path.

Public outputs must not imply bundle sale, bundle delivery, bundle certification, bundle completeness or bundle customer entitlement.

## 9. Dispute Pack Boundary

Machine-readable output may not represent itself as a Dispute Pack.

A technical verification output is not legal argument, litigation strategy, dispute filing material, court-ready package or official dispute support.

Public outputs must not imply legal sufficiency, dispute success, institutional admissibility or customer-facing legal service.

## 10. Public Verifier Output Boundary

A public verifier may confirm that a bounded artifact is technically verifiable.

A public verifier must not certify the artifact.

A public verifier must not issue ARV authority.

A public verifier must not imply customer-specific review.

A public verifier must not imply that ARV has accepted, endorsed, certified, monetized, adjudicated or guaranteed the artifact.

## 11. API Output Boundary

A public API response must remain bounded to technical verification state.

It must not expose protected commercial logic, protected certificate issuance logic, customer evidence, private workflows, pricing logic, dispute automation, internal scoring, official certificate generation logic or protected ARV authority semantics.

Any future API output must be separately reviewed before public exposure.

## 12. Machine-Readable Field Boundary

Machine-readable fields must avoid authority inflation.

Forbidden field names include, without limitation:

- certificate_issued;
- official_certificate;
- certified_by_arv;
- legally_valid;
- court_ready;
- dispute_pack;
- evidence_certificate;
- bundle_evidence_package;
- customer_entitlement;
- authority_approved;
- official_issuance;
- adjudicated;
- guaranteed;
- accepted_by_court.

Permitted field names should remain bounded, technical and non-authoritative.

Examples include:

- artifact_hash;
- hash_algorithm;
- verification_status;
- manifest_status;
- chain_status;
- validation_scope;
- non_authoritative_result;
- technical_result;
- checked_at;
- verifier_version.

## 13. Human-Readable Parity

Any machine-readable output must have equivalent human-readable boundary language.

If a machine-readable output says that verification passed, the human-readable output must also clarify the bounded nature of the verification.

Machine-readable output must not silently escalate authority beyond the human-readable explanation.

## 14. No Customer Evidence Exposure

Machine-readable outputs must not expose customer-specific operational evidence, private evidence records, commercial workflows, protected dispute facts, protected certificate issuance metadata, identity-sensitive data, secrets, credentials or non-public customer materials.

No public output may make private evidence public by default.

## 15. Publication Gate

A future public candidate involving machine-readable outputs remains blocked until the project has completed:

- explicit machine-readable output boundary approval;
- public verifier wording review;
- Evidence Certificate terminology review;
- Bundle Evidence Package terminology review;
- Dispute Pack terminology review;
- authority wording review;
- API output review;
- field-name taxonomy review;
- protected commercial terminology exclusion review;
- customer evidence exclusion approval;
- independent governance review;
- signed GO / NO-GO decision.

No technical artifact may bypass the machine-readable output publication gate.

## 16. Audit Principle

ARV will not create machine-readable authority by accident.

Any future public machine-readable surface must be deliberately allowed, deliberately extracted, minimized, separately reviewed and independently auditable.

The protected certificate, bundle, dispute and commercial issuance system remains isolated behind the governance boundary.
